ЭКСПЕРИМЕНТ Б. ДВА ПРЕДСТАВЛЕНИЯ ФУНКЦИИ ПЕРЕХОДОВ СОБСТВЕННОГО СКАНЕРА

1. Вопрос и измеряемая величина

При фиксированном автомате и фиксированном входном слове как меняется время
полного лексического анализа при двух способах вычисления δ(q,a)?
Вариант table обращается к таблице (§ 2.6.1 «Интерпретаторы таблиц»).
Вариант branch кодирует переходы ветвлениями (§ 2.6.2 «Представление
автомата в программном коде»). Меняем способ представления δ в исходной
программе. Измеряем суммарное время выделения лексем до конца входа.
У этого измерения есть и общие затраты: выбор границы, возврат Token,
вызов next и учёт результата. Числа характеризуют сканер целиком.
Второй вопрос: сохраняется ли наблюдаемое отношение времён на входных
словах с разным лексическим составом?

2. Где что разместить

Следующие имена новых файлов и целей сборки — предложение для вашего дерева.
Сначала проверьте, что именно читает и порождает текущий generate_dfa.py.

  transitions.tsv         Существующее описание переходов. Если таблица уже
                          производится из другого источника, использовать
                          тот же источник и ту же нумерацию состояний.
  generate_dfa.py         Один генератор читает описание один раз и выпускает
                          таблицу и код ветвлений из одних разобранных данных.
  scanner_table.cpp       Общий алгоритм next и два экземпляра интерфейса.
snirs-dfa/tests/          Проверка равенства переходов и поведения сканеров.
experiments/b/
  experiment_b.c          Выбор двух Scanner и порядок парных запусков.

Не нужно заводить второй проект для branch. Добавьте в существующую цель

для C++ используйте тот же механизм C-связывания, через который сейчас
работает c_interface_test.c. Цель experiment_b связывается с C++-библиотекой
через CMake; experiment_b.c обращается к обоим сканерам через scanner.h.

3. Построить сравнимые реализации

а) Из графа (§ 2.1.3) и таблицы (§ 2.1.2) выписать Q, q0, заключительные
состояния, соответствующие им виды лексем и принятую обработку отсутствующего
перехода (§ 2.1.4). Зафиксировать поведение конца входа отдельно. Байт 0x00
внутри файла — обычный входной байт согласно scanner_spec.txt.

б) Проверить, как текущая таблица индексируется символом. Если уже есть
функция class_of(byte), оба варианта вызывают одну и ту же функцию.
При таблице по отдельным байтам оба используют непосредственно байт.
Пример для случая с классами:
    table:  next_state = transitions[q][class_of(a)]
    branch: switch (q) { case ...: switch (class_of(a)) { ... } }
Пустой переход и все допустимые переходы кодировать одинаковыми результатами.
Если таблица хранит служебные состояния, включить их в проверку по их смыслу.

в) Общий код next начинает лексему, запоминает последнюю заключительную
позицию, обрабатывает пропуски, ошибку и EOF. Различается лишь выражение,
вычисляющее следующее состояние. Для существующего C++ удобен общий шаблон
next_impl<step>: инстанцировать его с table_step и branch_step. У каждого
варианта свой указатель next в Scanner; open и close могут быть общими.
Так в одном варианте случайно не появится лишний косвенный вызов на байт.
Обе версии собирать одним компилятором с одинаковыми флагами. Компилятор
может превратить switch в таблицу переходов управления. Формулировать вывод
для проверенных исходных представлений и конкретной сборки.

4. Сначала подтвердить корректность

а) Перебрать каждое состояние q и каждый байт a от 0 до 255, если интерфейс
принимает байты. Проверить table_step(q,a) == branch_step(q,a) через тот же
путь классификации символа, который использует сканер. При первом расхождении
напечатать q, a и оба результата. Зафиксировать число проверенных пар.

б) На коротких примерах сверить обе реализации с ответами, выписанными
вручную: if, if2, if:=15, пустой файл, комментарий до конца файла и ошибка.
Проверять виды, границы и повторный next после ошибки или EOF.

в) На каждом нагрузочном файле пройти сканерами одновременно и сравнить
каждую тройку (kind,begin,end), включая конец. Любой TOK_ERROR на таком входе
останавливает подготовку замеров. Совпадение двух ошибочных ответов
в середине файла не означает, что файл обработан. Контрольная сумма во время
измерения дополняет эту полную сверку.

5. Взять готовый учебный материал

Посмотреть содержимое pseudocode/run.txt и pseudocode/pseudocode.txt.
Выбрать уже подготовленную текстовую запись, которая соответствует
spec/scanner_spec.txt, и зафиксировать её как вход textbook. По одному
названию run.txt его пригодность определить нельзя. Сырой текст учебника
может содержать штрихи, греческие буквы и символьные литералы. Уточнения
текстовой записи фиксировать в существующем pseudocode_translation.json.
Указать исходные параграфы. Проверить полное чтение по п. 4в.

Сохранить число байтов, лексем и распределение видов. Число строк —
описательная характеристика. Для короткого исходника сделать один более
длинный файл из целых копий, вставляя между ними LF. Записать число копий
и хеш фактического входа. Копии остаются одним учебным образцом.

6. Построить управляемые серии входов

Общий Python-генератор один раз записывает байты файлов. Сканеры затем читают
одни и те же файлы. Достаточен следующий детерминированный набор.

I. Общие начала ключевых слов и идентификаторов. Файл из блока «ifx »
и файл из «abx » (кавычки обозначают границы блока; пробел входит в блок).
Повторить каждый блок 262144 раза: по 1 МиБ, 262144 идентификатора, те же
позиции, длины и разделители. В отдельном диагностическом проходе посмотреть
пути по графу. Если ключевые слова распознаются поздней проверкой по словарю,
пути δ для этих идентификаторов могут совпадать. Тогда это контрольная пара;
для исследования различных путей дополнительно выбрать по automaton.dot два
слова одной длины и одного вида с действительно различными путями.

II. Частое и редкое завершение лексемы. Построить файл из блока «aaa »
и файл из блока «aaaaaaaaaaaaaaa » (15 букв и пробел). Повторять до ровно
1 МиБ. В первом файле 262144 идентификатора, во втором 65536. Нагрузка
меняет и частоту разделителей. Вывод относится к обработке всего такого
текста; отдельно цену одного завершения эта серия не измеряет.

III. Комментарии и пропуски. Единица входа — байт x и восемь последующих
байтов. В первой версии после x идут семь пробелов и LF, во второй —
два знака /, пять букв a и LF. Повторить по 131072 единицы каждого вида.
Размер, число выданных лексем и их границы совпадают. Меняется способ,
которым автомат проходит пропускаемый участок. Для I–III сравнивать
таблицу и ветвления внутри каждого файла, затем отношения между файлами.

IV. Размер входного слова. Повторять один смешанный блок из согласованных
лексем. Например, байты ASCII «if x:=15 then return x end if», затем LF.
Использовать 2048, 32768 и 524288 полных копий. Записать фактические размеры.
При росте длины доли видов лексем и разделителей сохраняются. Для I–IV
параметров повторения достаточно для воспроизведения. Если позже добавите
случайное перемешивание, сохранить алгоритм и начальное значение генератора.

В перечне входов записать имя, семейство, рецепт, bytes, tokens, SHA-256,
а для учебного примера — источник. Вся совокупность представляет выбранные
случаи работы сканера на согласованной лексике. Она не даёт распределения
скоростей по всем возможным программам.

7. Измерить время

а) Собирать обе реализации в Release. Вначале сделать пробный запуск на
учебном файле: он должен доходить до EOF и давать тот же результат, что п. 4.
Время коротких прогонов сравнить с ценой двух чтений часов. Если величины
сопоставимы, перед основной серией увеличить файл целыми копиями.

б) Программа читает файл в память один раз. Для каждого полного прохода:
    s = scanner.open(data, bytes); проверить успешное открытие
    подготовить счётчик K и начальное значение контрольной суммы
    t0 = показание монотонных часов
    вызывать scanner.next(s) в цикле; при обычной лексеме обновлять K
        и checksum по kind, begin, end; на EOF завершить цикл
    t1 = показание тех же часов
    scanner.close(s); проверить K и checksum; записать (t1−t0) в наносекундах
Например, для Linux подходят clock_gettime(CLOCK_MONOTONIC, ...).
Сверка содержимого, диагностические счётчики переходов, печать и запись CSV
выполняются за пределами таймера. Новое открытие перед каждым проходом
возвращает сканер в исходное состояние.

в) Один прогрев каждой реализации на каждом файле. Затем 16 парных раундов.
В нечётных сначала table, в чётных сначала branch. Так у каждой реализации
ровно восемь первых и восемь вторых запусков. Внутри раунда оба читают один
файл. Не запускать варианты одновременно. Сохранить все замеры, версии
исходников и параметры сборки. Первые два прогона для прогрева в CSV замеров
не включать. Получаем характеристики повторного сканирования текста в памяти.

8. Представить результат и сделать вывод

Для каждого входа вывести N байтов, K лексем, медиану [Q1; Q3] в нс/байт
для table и branch, а также медиану [Q1; Q3] парных отношений table/branch.
Схема исходных записей дана в experiment_results.txt. Сначала разобрать
учебный текст, затем сопоставить парные входы I и III, частоту завершений
в серии II и рост размера в IV. Для связи с графом можно отдельным запуском
подсчитать посещения состояний. Это даёт основание обсуждать различия путей;
выводы о кеше или предсказании ветвлений требуют отдельных измерений.

Форма вывода: «На входе ___ при N=___ и K=___ табличное представление дало
___ нс/байт, ветвления — ___. Медиана парного отношения ___, Q1–Q3 ___.
При изменении ___ отношение ___.» Если порядок результатов меняется между
раундами и отношение колеблется около единицы, указать, что в этой серии
устойчивое преимущество установить не удалось. Не объявлять победителя
по лучшему одиночному времени.

Готовность опыта: равенство δ проверено на всех парах, каждый вход пройден
до EOF с одинаковой выдачей, для каждого файла есть 16 пар замеров, а из
сохранённых CSV можно заново получить сводку и каждый численный вывод.
